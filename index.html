Aula 01

O que é versionamento, Git e GitHub

Antes de digitar qualquer comando, você precisa entender o problema que o Git resolve.

Seja sincero comigo: você já teve uma pasta parecida com essa aqui?

trabalho.docx
trabalho_final.docx
trabalho_final_v2.docx
trabalho_final_v2_agora_vai.docx
trabalho_FINAL_MESMO_revisado.docx

Pois é. Isso é controle de versão feito na mão. Funciona? Mais ou menos. Mas você não sabe o que mudou de uma versão para outra, não sabe quem mudou, e se duas pessoas editarem ao mesmo tempo... vira bagunça. Agora imagina isso num sistema com milhares de arquivos e dezenas de programadores.

O que é o Git

O Git é um sistema de controle de versão distribuído. Ele foi criado em 2005 por Linus Torvalds, o mesmo criador do Linux, para gerenciar o código do próprio kernel do Linux. Hoje é o padrão absoluto do mercado.

Na prática, o Git fica "vigiando" uma pasta do seu projeto. Sempre que você quiser, tira uma foto do estado dos arquivos. Cada foto dessas se chama commit. Com isso você consegue:

  • Voltar para qualquer versão anterior do projeto, a qualquer momento;
  • Ver exatamente o que mudou, linha por linha, quem mudou e quando;
  • Trabalhar em várias funcionalidades ao mesmo tempo sem uma atrapalhar a outra (as branches);
  • Juntar o trabalho de várias pessoas no mesmo projeto com segurança.

E o "distribuído" significa que cada pessoa tem uma cópia completa do histórico no próprio computador. Você consegue trabalhar offline, fazer commits no avião, e só sincronizar depois.

O que é o GitHub

O GitHub é um serviço na internet que hospeda repositórios Git. Ele guarda uma cópia do seu projeto na nuvem e adiciona um monte de ferramentas de colaboração em cima: Pull Requests, Issues, revisão de código, Actions (automação), páginas web e muito mais. Ele também funciona como uma vitrine: é o seu portfólio de programador.

Analogia para nunca mais confundir

O Git é a câmera fotográfica. Ela tira as fotos (commits) e organiza o álbum, e funciona sozinha, no seu computador, sem internet.
O GitHub é a rede social onde você publica e compartilha esse álbum com outras pessoas. Existem outras "redes sociais" parecidas, como GitLab e Bitbucket, mas a câmera é sempre a mesma: o Git.

Aula 03

Configuração inicial: dizendo ao Git quem é você

Configurações que você faz uma vez só por computador.

Todo commit no Git leva uma "assinatura": nome e e-mail do autor. Então a primeira coisa a fazer é se apresentar. Use o mesmo e-mail da sua conta do GitHub (ou que você vai usar para criar a conta), assim seus commits aparecem ligados ao seu perfil.

# quem é você (obrigatório)
$ git config --global user.name "Ana Souza"
$ git config --global user.email "ana@exemplo.com"

# nome padrão da branch inicial
$ git config --global init.defaultBranch main

# deixa a saída colorida
$ git config --global color.ui auto

Editor padrão

Em alguns momentos o Git abre um editor de texto (para escrever uma mensagem de commit longa, por exemplo). Por padrão ele abre o Vim, e muita gente fica presa lá dentro. Vamos trocar para o VS Code:

$ git config --global core.editor "code --wait"
Caiu no Vim sem querer?

Respira. Aperte Esc, digite :wq e Enter para salvar e sair. Ou :q! e Enter para sair sem salvar. Pronto, você está livre.

Finais de linha (importante para quem mistura sistemas)

Windows marca o fim de cada linha de um jeito (CRLF) e Linux/macOS de outro (LF). Se uma equipe mistura sistemas e ninguém configura isso, o Git acha que todas as linhas mudaram. A regra é: no repositório fica LF, e cada sistema converte na hora certa.

# converte para CRLF ao baixar e para LF ao comitar
$ git config --global core.autocrlf true

# garante LF ao comitar, sem mexer no que você baixa
$ git config --global core.autocrlf input

# garante LF ao comitar, sem mexer no que você baixa
$ git config --global core.autocrlf input

Conferindo suas configurações

$ git config --list
$ git config --list --show-origin   # mostra de qual arquivo veio cada config
$ git config user.name               # consulta uma config específica
Ana Souza

Aula 04

Como o Git pensa: as três áreas

Esta é a aula mais importante do manual. Entendeu isso, entendeu o Git.

Presta atenção aqui, porque é aqui que a maioria das pessoas se perde. Seus arquivos, dentro de um projeto com Git, podem estar em três lugares (e um quarto, quando entra o GitHub):

Diretório de trabalho

A pasta que você vê e edita no seu editor. É aqui que você cria, altera e apaga arquivos. O Git apenas observa.

Staging area

Uma "sala de espera". Você escolhe com git add quais mudanças vão entrar no próximo commit.

Repositório local

O histórico de commits, guardado na pasta oculta .git. Cada git commit grava uma foto aqui.

Repositório remoto

Uma cópia do repositório num servidor, como o GitHub. Você envia com git push e recebe com git pull.

Analogia: a foto da formatura

O diretório de trabalho é o salão da festa, com todo mundo circulando. O git add é o fotógrafo chamando quem vai sair na foto: "você, você e você, vem pra cá". A staging area é o grupo posicionado na frente da câmera. O git commit é o clique, e a foto vai para o álbum (o repositório). E o git push é postar o álbum na internet.

Por que não tirar foto de todo mundo direto? Porque às vezes você mexeu em cinco arquivos, mas só três fazem parte da mesma tarefa. A staging area deixa você montar commits organizados.

O ciclo de vida de um arquivo

Commit, hash e HEAD

Cada commit recebe uma identidade única chamada hash, uma sequência de 40 caracteres como 3f9a1c27e5b0.... Na prática a gente usa só os 7 primeiros: 3f9a1c2. Cada commit também aponta para o commit anterior (o "pai"). Isso forma uma corrente:

  • Branch (como main) é só uma etiqueta que aponta para um commit e anda sozinha quando você faz um novo commit.
  • HEAD é o "você está aqui" do mapa do shopping. Normalmente aponta para a branch em que você está.
  • HEAD~1 é o commit anterior ao HEAD, HEAD~2 o de antes, e assim por diante. Você vai usar muito isso.
Desafio 4

Desenhe num papel as quatro áreas e escreva, nas setas, qual comando leva uma mudança de uma área para a outra. Se conseguir fazer de memória, você dominou a teoria que sustenta todo o resto.

Aula 05

Mão na massa: seu primeiro repositório

Criar um repositório, fazer os primeiros commits e entender o que o Git responde.

Chega de teoria. Bora pra prática! Vamos criar um mini site pessoal e versionar ele.

Passo 1: criar a pasta e iniciar o Git

$ cd ~/Documents
$ mkdir meu-site
$ cd meu-site
$ git init
Initialized empty Git repository in C:/Users/Ana/Documents/meu-site/.git/

$ cd ~
$ mkdir meu-site
$ cd meu-site
$ git init
Initialized empty Git repository in /home/ana/meu-site/.git/

$ cd ~/Documents
$ mkdir meu-site
$ cd meu-site
$ git init
Initialized empty Git repository in /Users/ana/Documents/meu-site/.git/

O git init criou uma pasta oculta chamada .git. Ela É o repositório. Todo o histórico mora ali dentro. Se você apagar essa pasta, o projeto volta a ser uma pasta comum, sem histórico nenhum.

Cuidado!

Não rode git init na sua pasta pessoal inteira, nem na Área de Trabalho. Sempre dentro da pasta de um projeto específico. E nunca mexa manualmente nos arquivos de dentro do .git.

Passo 2: o comando que você mais vai usar

$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

O git status é o seu melhor amigo. Na dúvida, git status. Ele diz em que branch você está e em que estado cada arquivo se encontra.

Passo 3: criar arquivos

Crie os arquivos no seu editor ou direto pelo terminal:

$ echo "# Meu Site" > README.md
$ echo "<h1>Olá, mundo!</h1>" > index.html
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md
        index.html
Usuário de Windows, atenção

Rode o echo ... > no Git Bash. No PowerShell antigo (5.1) esse comando grava o arquivo em UTF-16 e o Git passa a tratá-lo como binário. Se preferir, crie os arquivos pelo VS Code.

Tudo certo por aqui: o echo funciona igualzinho no seu terminal.

Tudo certo por aqui: o echo funciona igualzinho no seu Terminal (zsh).

Passo 4: preparar (git add)

$ git add README.md index.html
$ git status
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md
        new file:   index.html

Outras formas de usar o git add, para você consultar quando precisar:

$ git add README.md        # um arquivo específico
$ git add a.html b.css     # vários arquivos de uma vez
$ git add .                # tudo da pasta atual para baixo
$ git add -A               # tudo do repositório (inclusive arquivos apagados)
$ git add "*.html"         # por padrão de nome

Passo 5: comitar (git commit)

$ git commit -m "Cria estrutura inicial do site"
[main (root-commit) 3f9a1c2] Cria estrutura inicial do site
 2 files changed, 2 insertions(+)
 create mode 100644 README.md
 create mode 100644 index.html

Olha só o que o Git respondeu: a branch (main), o hash curto (3f9a1c2), a sua mensagem e um resumo do que mudou. Foto tirada!

Variações úteis do commit

# abre o editor para escrever título e descrição longos
$ git commit

# título + corpo pela linha de comando
$ git commit -m "Adiciona página de contato" -m "Inclui formulário e link para e-mail."

# atalho: add + commit de arquivos JÁ RASTREADOS (não pega arquivos novos!)
$ git commit -am "Corrige erro de digitação no título"

Passo 6: ver o histórico

$ git log
commit 3f9a1c27e5b04d6a9e1f2b3c4d5e6f7a8b9c0d1e (HEAD -> main)
Author: Ana Souza <ana@exemplo.com>
Date:   Sun Oct 25 10:30:00 2026 -0300

    Cria estrutura inicial do site

$ git log --oneline
3f9a1c2 (HEAD -> main) Cria estrutura inicial do site
O ciclo que você vai repetir mil vezes

Edita → git status → git add → git commit. Grave esse mantra. Faça commits pequenos e frequentes, cada um com uma ideia só. Commit é de graça!

Desafio 5

No seu meu-site, crie um style.css e faça um commit só com ele. Depois edite o index.html e o README.md, mas comite apenas o index.html. Rode git status no final: o README deve continuar como "modified". Termine com git log --oneline mostrando 3 commits.

Aula 06

Investigando o histórico: log, show, diff e blame

Virar detetive do próprio código: o que mudou, quando, e quem mudou.

git log: todas as formas de ver o histórico

$ git log --oneline                    # uma linha por commit
$ git log --oneline --graph --all      # desenha as branches no terminal
$ git log -n 5                         # só os 5 últimos
$ git log --stat                       # quais arquivos mudaram em cada commit
$ git log -p                           # mostra o código alterado (patch)
$ git log --author="Ana"               # commits de uma pessoa
$ git log --since="2 weeks ago"        # das últimas 2 semanas
$ git log --until="2026-09-30"         # até uma data
$ git log --grep="login"               # busca na mensagem do commit
$ git log -S "calcularFrete"           # commits que adicionaram/removeram esse texto
$ git log -- index.html                # histórico de um arquivo
$ git log --follow -- src/app.js       # segue o arquivo mesmo se foi renomeado
$ git log main..feature                # commits que estão na feature e não na main
$ git log --pretty=format:"%h %an %ar - %s"
3f9a1c2 Ana Souza 2 hours ago - Cria estrutura inicial do site
Saindo do log

Quando o histórico é grande, o Git abre um "paginador". Use Espaço para descer uma página, ↑/↓ para rolar, / para buscar e q para sair.

git show: abrindo um commit

$ git show                     # o último commit (HEAD)
$ git show 3f9a1c2             # um commit específico
$ git show HEAD~2              # dois commits atrás
$ git show HEAD~1:index.html   # o conteúdo do arquivo naquele commit
$ git show --stat 3f9a1c2      # só o resumo

git diff: o que mudou exatamente

Linhas com + (verde) foram adicionadas; linhas com - (vermelho) foram removidas. Agora, presta atenção em o que está sendo comparado em cada caso:

ComandoCompara
git diffDiretório de trabalho × staging (o que você ainda não adicionou)
git diff --stagedStaging × último commit (o que vai entrar no próximo commit)
git diff HEADTudo que mudou desde o último commit
git diff HEAD~3 HEADDois commits quaisquer
git diff main featureDuas branches
git diff --statSó o resumo por arquivo
git diff --name-onlySó os nomes dos arquivos alterados
git diff --word-diffDestaca palavras, ótimo para textos
 
$ git diff
diff --git a/index.html b/index.html
--- a/index.html
+++ b/index.html
@@ -1 +1,2 @@
-<h1>Olá, mundo!</h1>
+<h1>Olá, eu sou a Ana!</h1>
+<p>Desenvolvedora em formação.</p>

git blame e shortlog: quem fez o quê

$ git blame index.html          # autor e commit de cada linha
$ git blame -L 10,25 app.js     # só das linhas 10 a 25
$ git shortlog -sn              # ranking de commits por pessoa
    42  Ana Souza
    17  Bruno Lima
Blame não é para culpar ninguém

Apesar do nome ("culpar"), use o blame para entender o contexto: encontrar o commit que mudou aquela linha e ler a mensagem que explica o porquê.

Desafio 6

No seu projeto, edite o index.html sem dar add e compare a saída de git diff e git diff --staged. Depois dê add e compare de novo. Explique para você mesmo por que as saídas trocaram de lugar.

Aula 07

Desfazendo coisas: a máquina do tempo

Errou? Tudo bem. Aqui você aprende a voltar atrás em cada uma das áreas.

Essa é a parte em que o Git salva a sua pele. A regra é: primeiro identifique em que área está o erro, depois escolha o comando.

Desfazendo no diretório de trabalho e na staging

# descarta as alterações que você ainda NÃO adicionou (git add)
$ git restore index.html

# o mesmo, para todos os arquivos
$ git restore .

# tira um arquivo da staging, mas MANTÉM suas alterações
$ git restore --staged index.html

# volta o arquivo exatamente ao último commit (staging e disco)
$ git restore --staged --worktree index.html

# traz um arquivo de como ele estava 3 commits atrás
$ git restore --source=HEAD~3 index.html
Comandos antigos que você vai ver por aí

Em tutoriais mais antigos aparecem git checkout -- arquivo (igual a git restore arquivo) e git reset HEAD arquivo (igual a git restore --staged arquivo). Funcionam até hoje, mas o restore é mais claro.

Consertando o último commit: --amend

# errou a mensagem?
$ git commit --amend -m "Mensagem corrigida"

# esqueceu um arquivo?
$ git add arquivo-esquecido.css
$ git commit --amend --no-edit

O --amend substitui o último commit por um novo (o hash muda). Use só em commits que você ainda não enviou para o GitHub.

git reset: voltando a branch para trás

O git reset move a branch atual para um commit anterior. A diferença entre os modos é o que acontece com as mudanças dos commits que "sumiram":

ComandoCommitsStagingSeus arquivosPerigo
git reset --soft HEAD~1DesfeitosMudanças ficam preparadasIntactosBaixo
git reset HEAD~1 (--mixed, padrão)DesfeitosEsvaziadaIntactos (mudanças viram "modified")Baixo
git reset --hard HEAD~1DesfeitosEsvaziadaMudanças APAGADASAlto
 
# "quero refazer o último commit, mas manter tudo pronto para comitar"
$ git reset --soft HEAD~1

# "quero desfazer os 3 últimos commits e reorganizar os arquivos"
$ git reset HEAD~3

# "quero jogar fora tudo e voltar exatamente para esse commit"
$ git reset --hard 8b21e07
Cuidado com o --hard

Alterações que nunca foram comitadas e são apagadas pelo --hard não voltam mais. Já commits "perdidos" ainda dá para recuperar com o git reflog (Aula 17). E nunca use reset em commits que outras pessoas já baixaram do GitHub.

git revert: desfazendo com segurança

O revert não apaga nada. Ele cria um commit novo que faz exatamente o contrário do commit escolhido. É o jeito certo de desfazer algo que já está no GitHub.

$ git revert c4d0f55
$ git revert --no-edit c4d0f55     # sem abrir o editor
$ git revert HEAD~2..HEAD          # reverte um intervalo de commits

Removendo, renomeando e limpando arquivos

$ git rm arquivo.txt              # apaga do disco e prepara a remoção
$ git rm --cached senha.txt       # para de rastrear, mas mantém no disco
$ git rm -r --cached node_modules # o mesmo, para uma pasta
$ git mv antigo.js novo.js        # renomeia/move e o Git entende como renomeação

$ git clean -n                    # SIMULA: mostra arquivos não rastreados que seriam apagados
$ git clean -f                    # apaga arquivos não rastreados
$ git clean -fd                   # apaga arquivos e pastas não rastreados

Desafio 7

Faça um commit de propósito com uma mensagem errada e corrija com --amend. Depois faça mais dois commits e desfaça-os com git reset --soft HEAD~2: confira com git status que as mudanças continuam preparadas. Por fim, crie um commit "quebrado" e desfaça-o com git revert.

Aula 08

O arquivo .gitignore

Ensinar o Git a ignorar o que não deve ser versionado.

Nem tudo deve ir para o repositório. Dependências que podem ser baixadas de novo (node_modules), arquivos compilados, logs, configurações do seu editor e, principalmente, senhas e chaves (.env). Para isso existe o .gitignore: um arquivo de texto na raiz do projeto com uma regra por linha.

# dependências
node_modules/
vendor/

# variáveis de ambiente e segredos
.env
.env.*
# o ! cria uma exceção: ESTE arquivo será versionado
!.env.example

# builds e arquivos gerados
dist/
build/
*.pyc
__pycache__/

# logs
*.log

# arquivos do sistema (macOS e Windows) e de editores
.DS_Store
Thumbs.db
.vscode/
.idea/

# só na raiz do projeto
/config-local.json

# em qualquer nível de pasta
**/temp/
PadrãoSignifica
*.logQualquer arquivo terminado em .log
pasta/Uma pasta inteira (com tudo dentro)
/arquivoSó na raiz do projeto
**/nomeEm qualquer subpasta
!arquivoExceção: não ignorar este
#Comentário (só no início da linha)
Comentário sempre em linha própria

No .gitignore, o # só vira comentário quando é o primeiro caractere da linha. Uma linha como .env # segredos faz o Git procurar um arquivo chamado literalmente ".env # segredos", e o seu .env não é ignorado.

"Coloquei no .gitignore e continua aparecendo!"

O .gitignore só vale para arquivos que ainda não são rastreados. Se o arquivo já foi comitado antes, tire-o do rastreamento:

$ git rm --cached .env
$ git commit -m "Remove .env do repositório"

Um .gitignore global para o seu computador

Arquivos do seu sistema e editor (como .DS_Store ou Thumbs.db) podem ir num ignore global, valendo para todos os projetos:

$ echo "Thumbs.db" >> ~/.gitignore_global
$ echo "desktop.ini" >> ~/.gitignore_global
$ git config --global core.excludesfile ~/.gitignore_global

$ echo "*~" >> ~/.gitignore_global
$ echo ".directory" >> ~/.gitignore_global
$ git config --global core.excludesfile ~/.gitignore_global

$ echo ".DS_Store" >> ~/.gitignore_global
$ git config --global core.excludesfile ~/.gitignore_global

# descobre qual regra está ignorando um arquivo
$ git check-ignore -v debug.log
.gitignore:14:*.log    debug.log
Não precisa escrever do zero

Ao criar um repositório no GitHub, há a opção Add .gitignore com modelos prontos para Node, Python, Java etc. O repositório público github/gitignore reúne esses modelos.

Desafio 8

Crie um arquivo .env com SENHA=123 e uma pasta logs/ com um arquivo dentro. Escreva um .gitignore que ignore os dois, comite o .gitignore e confirme com git status que eles sumiram da lista.

Aula 09

Branches: universos paralelos do seu projeto

Criar, trocar, renomear e apagar branches sem medo.

Imagina que seu site está funcionando e você quer testar um layout novo. Se mexer direto na main e der errado, quebrou o site. A solução é criar uma branch (ramificação): uma linha do tempo paralela onde você experimenta à vontade.

E a melhor parte: criar uma branch no Git é instantâneo e não ocupa espaço. Ela é só uma etiqueta apontando para um commit. Por isso o normal é criar uma branch para cada funcionalidade ou correção.

Comandos de branch

# listar
$ git branch               # branches locais (* marca a atual)
$ git branch -v            # com o último commit de cada uma
$ git branch -a            # locais + remotas
$ git branch -vv           # mostra qual branch remota cada uma acompanha

# criar
$ git branch novo-layout           # cria (mas continua na atual)
$ git switch novo-layout           # muda para ela
$ git switch -c novo-layout        # cria E muda (o mais usado!)
$ git switch -c hotfix 8b21e07     # cria a partir de um commit específico

# navegar
$ git switch main                  # volta para a main
$ git switch -                     # volta para a branch anterior

# renomear e apagar
$ git branch -m nome-novo          # renomeia a branch atual
$ git branch -m antigo novo        # renomeia outra branch
$ git branch -d novo-layout        # apaga (só se já foi mesclada)
$ git branch -D experimento        # força apagar, mesmo sem merge

# quais já foram mescladas na atual?
$ git branch --merged
$ git branch --no-merged
E o git checkout?

Antes do switch existir, tudo era feito com checkout: git checkout nome troca de branch e git checkout -b nome cria e troca. Você vai encontrar isso em muito tutorial e funciona perfeitamente. O switch só deixa a intenção mais clara.

Dê nomes que contam uma história

Padrões comuns: feature/carrinho-de-compras, fix/erro-no-login, docs/atualiza-readme, hotfix/pagamento-pix. Sem espaços nem acentos.

Trocar de branch com mudanças pendentes

Se você tem alterações não comitadas que conflitam com a outra branch, o Git não deixa trocar. Comite antes, ou guarde temporariamente com git stash (Aula 15).

Desafio 9

Crie a branch feature/rodape, adicione um rodapé no index.html e faça dois commits. Volte para a main e abra o arquivo: o rodapé sumiu! Volte para a feature e ele reaparece. Termine com git log --oneline --graph --all.

Aula 10

Merge e conflitos: juntando os universos

Mesclar branches e resolver conflitos com calma.

Terminou a funcionalidade na branch? Hora de trazer ela para a main. A regra de ouro: vá para a branch que vai RECEBER as mudanças e depois peça o merge.

$ git switch main
$ git merge feature/rodape

Os dois tipos de merge

1. Fast-forward (avanço rápido)

Se a main não andou desde que a branch foi criada, o Git só "empurra" a etiqueta main para frente. Nenhum commit novo é criado.

2. Merge de três vias (merge commit)

Se as duas branches andaram, o Git cria um commit de merge com dois pais, juntando as duas histórias.

$ git merge feature                 # merge normal
$ git merge --no-ff feature         # força criar o commit de merge (registra que houve uma branch)
$ git merge --squash feature        # junta TODOS os commits da branch em um só, para você comitar
$ git commit -m "Adiciona rodapé"   # (necessário depois do --squash)
$ git merge --abort                 # cancela um merge em andamento

Conflitos: não entre em pânico!

Um conflito acontece quando as duas branches mudaram a mesma linha do mesmo arquivo. O Git não tem como adivinhar qual versão está certa, então ele para e pede a sua ajuda. É normal, acontece todo dia em qualquer empresa.

$ git merge feature/titulo
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

$ git status
You have unmerged paths.
Unmerged paths:
        both modified:   index.html

Abra o arquivo e você vai ver isso aqui:

<<<<<<< HEAD
<h1>Bem-vindo ao meu portfólio</h1>
=======
<h1>Olá! Eu sou a Ana</h1>
>>>>>>> feature/titulo
  • Entre <<<<<<< HEAD e =======: a versão da branch em que você está (a main).
  • Entre ======= e >>>>>>>: a versão que está chegando.

Como resolver, passo a passo

  1. Edite o arquivo deixando o conteúdo final do jeito certo (uma versão, a outra ou uma mistura das duas).
  2. Apague as linhas de marcação <<<<<<<, ======= e >>>>>>>.
  3. Marque como resolvido com git add.
  4. Finalize com git commit.
$ git add index.html
$ git commit -m "Mescla feature/titulo resolvendo conflito no título"

# atalhos: ficar inteiramente com uma das versões de um arquivo
$ git checkout --ours index.html     # mantém a versão da branch atual
$ git checkout --theirs index.html   # mantém a versão que está chegando

# lista só os arquivos ainda em conflito
$ git diff --name-only --diff-filter=U
O VS Code resolve isso com cliques

Ao abrir um arquivo em conflito no VS Code, aparecem botões acima de cada trecho: Accept Current Change, Accept Incoming Change, Accept Both Changes. Também dá para usar git mergetool com a ferramenta que você preferir.

Desafio 10

Provoque um conflito de propósito: crie a branch titulo-novo e mude o <h1>. Volte para a main e mude o mesmo <h1> de outro jeito. Comite nas duas e faça o merge. Resolva o conflito juntando as duas ideias.

Aula 11

GitHub: criando a conta e se autenticando

Deixar seu computador autorizado a enviar código para o GitHub.

Criando a conta

  1. Acesse github.com e clique em Sign up.
  2. Use o mesmo e-mail que você configurou no git config user.email.
  3. Escolha um nome de usuário profissional: ele vira o endereço do seu portfólio (github.com/seu-usuario).
  4. Ative a autenticação em dois fatores (2FA) em Settings → Password and authentication. O GitHub passou a exigir o 2FA das contas que contribuem com código, então é melhor já deixar ativado.
Sua senha do GitHub NÃO funciona no terminal

Desde 2021 o GitHub não aceita a senha da conta para operações do Git. Se o terminal pedir senha e você digitar a do site, vai dar Authentication failed. Você precisa de uma das três formas abaixo.

Opção A: HTTPS

Com o Git Credential Manager ou o GitHub CLI. Abre o navegador para você logar. Mais fácil para iniciantes.

Opção B: SSH

Uma chave criptográfica guardada no seu computador. Configura uma vez e nunca mais pede nada. Preferida por desenvolvedores.

Opção C: Token

Um Personal Access Token gerado no site e usado no lugar da senha. Útil em servidores e automações.

Opção A: HTTPS com login pelo navegador

Se você instalou o Git com o Git Credential Manager (padrão do instalador), não precisa fazer nada agora. No primeiro git push, vai abrir uma janela para você entrar no GitHub pelo navegador, e o Windows guarda a credencial.

Prefere o GitHub CLI? Instale e faça login:

$ winget install --id GitHub.cli
$ gh auth login

O jeito mais simples é o GitHub CLI (gh). Instale pelo gerenciador da sua distro (no Ubuntu/Debian, sudo apt install gh; em versões mais antigas siga as instruções em cli.github.com) e rode:

$ gh auth login
? Where do you use GitHub? GitHub.com
? What is your preferred protocol for Git operations? HTTPS
? Authenticate Git with your GitHub credentials? Yes
? How would you like to authenticate GitHub CLI? Login with a web browser

Instale o GitHub CLI com o Homebrew e faça login. As credenciais ficam no Keychain do macOS.

$ brew install gh
$ gh auth login

Opção B: SSH (passo a passo)

1. Gere a chave (igual em todos os sistemas)

$ ssh-keygen -t ed25519 -C "ana@exemplo.com"
Enter file in which to save the key: [Enter para aceitar o padrão]
Enter passphrase: [uma senha para proteger a chave, recomendado]

Isso cria dois arquivos na pasta ~/.ssh: id_ed25519 (a chave privada, que nunca sai do seu computador) e id_ed25519.pub (a chave pública, que você vai entregar ao GitHub).

2. Coloque a chave no agente e copie a pública

$ eval "$(ssh-agent -s)"
$ ssh-add ~/.ssh/id_ed25519
$ clip < ~/.ssh/id_ed25519.pub     # copia para a área de transferência

Quer que o agente inicie sozinho com o Windows? No PowerShell como Administrador:

$ Get-Service ssh-agent | Set-Service -StartupType Automatic
$ Start-Service ssh-agent
$ ssh-add $env:USERPROFILE\.ssh\id_ed25519

Atenção: o Git para Windows usa, por padrão, o SSH que vem junto com ele, e não o do Windows. Para o Git aproveitar esse agente do Windows, diga a ele qual SSH usar:

$ git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"

$ eval "$(ssh-agent -s)"
$ ssh-add ~/.ssh/id_ed25519
$ cat ~/.ssh/id_ed25519.pub        # selecione e copie a saída

# ou, se tiver o xclip instalado:
$ xclip -sel clip < ~/.ssh/id_ed25519.pub

Primeiro crie (ou edite) o arquivo ~/.ssh/config com este conteúdo, para o macOS guardar a senha da chave no Keychain:

Host github.com
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519

$ eval "$(ssh-agent -s)"
$ ssh-add --apple-use-keychain ~/.ssh/id_ed25519
$ pbcopy < ~/.ssh/id_ed25519.pub   # copia para a área de transferência

3. Cadastre no GitHub e teste

No GitHub: foto de perfil → Settings → SSH and GPG keys → New SSH key. Dê um nome (ex.: "Notebook pessoal"), cole a chave pública e salve. Depois teste:

$ ssh -T git@github.com
Hi ana-souza! You've successfully authenticated, but GitHub does not provide shell access.

Apareceu o seu usuário? Perfeito! A partir de agora use as URLs no formato SSH: git@github.com:usuario/repo.git.

Nunca compartilhe a chave privada

O arquivo sem .pub é como a chave da sua casa. Não mande por e-mail, não coloque em repositório, não cole em lugar nenhum.

Desafio 11

Crie sua conta no GitHub, ative o 2FA e configure a autenticação SSH. Só passe para a próxima aula quando o ssh -T git@github.com responder com o seu nome de usuário (ou o gh auth status mostrar que você está logado).

Aula 12

Repositórios remotos: push, pull, fetch e clone

Sincronizar seu computador com o GitHub nos dois sentidos.

Cenário 1: já tenho um projeto local e quero subir para o GitHub

  1. No GitHub, clique em + → New repository. Dê o nome meu-site.
  2. Não marque README, .gitignore nem licença (seu projeto já tem histórico; isso evita conflito no primeiro envio).
  3. Copie a URL e rode no seu projeto:
$ git remote add origin git@github.com:ana-souza/meu-site.git
$ git branch -M main                # garante que a branch se chama main
$ git push -u origin main

O -u (ou --set-upstream) liga sua main local à main do GitHub. Só precisa dele na primeira vez. Depois disso é só git push e git pull.

Atalho com o GitHub CLI

Cria o repositório no GitHub, conecta e envia, tudo num comando só:

$ gh repo create meu-site --public --source=. --remote=origin --push

Cenário 2: o projeto já existe no GitHub e quero baixar

$ git clone git@github.com:ana-souza/meu-site.git
$ git clone https://github.com/ana-souza/meu-site.git outro-nome   # em outra pasta
$ git clone --depth 1 URL          # só o último commit (rápido para repos gigantes)
$ git clone -b develop URL         # já numa branch específica

O clone baixa o histórico completo e já configura o remoto origin automaticamente.

O dia a dia com remotos

# começar o dia: pegar o que a equipe enviou
$ git pull

# enviar seus commits
$ git push

# enviar uma branch nova pela primeira vez
$ git push -u origin feature/contato

# ver o que mudou no remoto ANTES de mesclar
$ git fetch
$ git log main..origin/main --oneline
$ git merge origin/main

# pull que reaplica seus commits por cima (histórico linear)
$ git pull --rebase

# limpa referências de branches que foram apagadas no GitHub
$ git fetch --prune

# apagar uma branch no GitHub
$ git push origin --delete feature/contato

Gerenciando remotos

$ git remote -v                                  # lista os remotos e URLs
$ git remote show origin                         # detalhes do remoto
$ git remote rename origin github                # renomeia
$ git remote remove github                       # remove
$ git remote set-url origin git@github.com:ana-souza/novo-nome.git   # troca a URL
"! [rejected] ... (fetch first)"

Esse erro significa que tem commits no GitHub que você ainda não tem. O Git se recusa a sobrescrever. A solução é trazer primeiro e enviar depois:

$ git pull --rebase
$ git push
git push --force

O --force sobrescreve o histórico do GitHub e pode apagar o trabalho de outras pessoas. Se realmente precisar (por exemplo, depois de um rebase na sua própria branch), use git push --force-with-lease, que recusa o envio se alguém tiver enviado algo que você ainda não viu. E nunca force na main compartilhada.

Desafio 12

Suba seu meu-site para o GitHub. Depois, edite o README.md pelo site do GitHub (ícone de lápis) e faça o commit por lá. Volte ao terminal, rode git fetch, veja a diferença com git log main..origin/main e então rode git pull.

Aula 13

Colaboração: fork, Pull Request, review e issues

Trabalhar em equipe e contribuir com projetos open source.

O GitHub Flow

É o fluxo de trabalho mais usado no mundo. Simples e poderoso:

  1. Crie uma brancha partir da main atualizada
  2. Faça commitspequenos e com boas mensagens
  3. Abra um Pull Requestpedindo para mesclar na main
  4. Revisãocolegas comentam, você ajusta com novos commits
  5. Mergeaprovado, a branch entra na main
  6. Limpezaapague a branch e atualize sua main

Pull Request (PR) na prática

Um Pull Request é um pedido: "por favor, puxem as mudanças da minha branch para a main". É ali que acontece a conversa, a revisão de código e os testes automáticos.

$ git switch main
$ git pull
$ git switch -c feature/pagina-contato
# ... edita, add, commit ...
$ git push -u origin feature/pagina-contato

Depois do push, o GitHub mostra um botão amarelo Compare & pull request. Clique, escreva um título claro, explique o que mudou e por quê, e clique em Create pull request. Ou pelo terminal:

$ gh pr create --fill                  # usa as mensagens dos commits
$ gh pr create --title "Adiciona página de contato" --body "Fecha #12"
$ gh pr list                           # PRs abertos
$ gh pr checkout 42                    # baixa a branch do PR 42 para revisar
$ gh pr merge 42 --squash --delete-branch

As três formas de mesclar um PR no GitHub

BotãoO que fazQuando usar
Create a merge commitMantém todos os commits e cria um commit de mergeQuando o histórico detalhado importa
Squash and mergeJunta todos os commits do PR em um sóO mais comum: deixa a main limpa
Rebase and mergeReaplica os commits em linha, sem commit de mergeTimes que preferem histórico linear
Palavras mágicas

Escreva Fixes #12 ou Closes #12 na descrição do PR: quando ele for mesclado, a issue 12 é fechada automaticamente.

Issues

Issues são a lista de tarefas do projeto: bugs, ideias, melhorias. Cada uma ganha um número (#12), pode ter responsável, etiquetas (labels) e marco (milestone). Use também os Projects do GitHub para montar um quadro Kanban.

$ gh issue create --title "Botão de enviar não funciona no celular" --label bug
$ gh issue list
$ gh issue view 12

Fork: contribuindo com projetos dos outros

Você não tem permissão para enviar direto para o repositório de outra pessoa. Então você faz um fork: uma cópia do repositório na sua conta. Trabalha nela e abre um PR para o original.

  1. No repositório original, clique em Fork.
  2. Clone o seu fork e adicione o original como upstream:
$ git clone git@github.com:ana-souza/projeto-legal.git
$ cd projeto-legal
$ git remote add upstream https://github.com/dono-original/projeto-legal.git
$ git remote -v
origin    git@github.com:ana-souza/projeto-legal.git (fetch)
origin    git@github.com:ana-souza/projeto-legal.git (push)
upstream  https://github.com/dono-original/projeto-legal.git (fetch)
upstream  https://github.com/dono-original/projeto-legal.git (push)

# trabalhe numa branch e envie para o SEU fork
$ git switch -c fix/erro-de-digitacao
$ git commit -am "Corrige erro de digitação na documentação"
$ git push -u origin fix/erro-de-digitacao
# agora abra o PR no GitHub, do seu fork para o original

# manter seu fork atualizado com o original
$ git switch main
$ git fetch upstream
$ git merge upstream/main
$ git push origin main

Atalho: no seu fork, o botão Sync fork faz essa atualização pelo site, ou gh repo fork dono/projeto --clone faz o fork e o clone de uma vez.

Arquivos que todo repositório deveria ter

README.md

A capa do projeto: o que é, como instalar, como usar, prints. Escrito em Markdown.

LICENSE

Diz o que os outros podem fazer com seu código (MIT, GPL, Apache...). Sem licença, ninguém pode reutilizar legalmente.

.gitignore

O que não deve ser versionado (Aula 08).

CONTRIBUTING.md

Regras para quem quer contribuir: padrões, como abrir PR, como rodar testes.

README de perfil

Crie um repositório com exatamente o mesmo nome do seu usuário. O README dele aparece no topo do seu perfil. É o seu cartão de visitas para recrutadores.

No seu meu-site, abra uma issue "Criar página de contato". Crie uma branch, implemente, envie e abra um PR com Closes #1 na descrição. Mescle com Squash and merge, apague a branch e veja a issue fechar sozinha. Depois atualize sua main local.

Aula 14

Rebase: reescrevendo a história com responsabilidade

Deixar o histórico linear e organizar commits antes de compartilhar.

O rebase faz o mesmo trabalho do merge (trazer mudanças de uma branch para outra), mas de um jeito diferente: ele pega seus commits e reaplica um por um em cima da outra branch, como se você tivesse começado o trabalho agora.

$ git switch feature
$ git rebase main

# se der conflito no meio do caminho:
#   resolva o arquivo, depois
$ git add arquivo-resolvido
$ git rebase --continue

$ git rebase --skip      # pula o commit problemático
$ git rebase --abort     # desiste e volta tudo como estava

# depois, a main pode receber a feature com um fast-forward
$ git switch main
$ git merge feature
A regra de ouro do rebase

Nunca faça rebase de commits que já foram compartilhados e que outras pessoas estão usando (como a main). O rebase cria commits novos, e quem já tinha os antigos vai ter um histórico que não bate mais. Rebase é para arrumar o seu trabalho antes de compartilhar.

Rebase interativo: a sala de edição

Com o -i você pode reordenar, juntar, renomear e apagar commits. Perfeito para limpar aquela sequência "teste", "agora vai", "corrige o corrige" antes de abrir um PR.

$ git rebase -i HEAD~4

Abre o editor com algo assim:

pick 1a2b3c4 Adiciona formulário de contato
pick 5d6e7f8 teste
pick 9a0b1c2 corrige o corrige
pick 3d4e5f6 Ajusta estilo do botão

# Commands:
# p, pick   = usa o commit como está
# r, reword = usa o commit, mas edita a mensagem
# e, edit   = para nesse commit para você alterar
# s, squash = junta com o commit anterior (mantém as duas mensagens)
# f, fixup  = junta com o anterior (descarta a mensagem deste)
# d, drop   = remove o commit

Troque pick pela ação desejada, salve e feche:

pick 1a2b3c4 Adiciona formulário de contato
fixup 5d6e7f8 teste
fixup 9a0b1c2 corrige o corrige
reword 3d4e5f6 Ajusta estilo do botão

Resultado: dois commits limpos no lugar de quatro bagunçados. Se a branch já estava no GitHub (só você usando), envie com git push --force-with-lease.

O truque do fixup automático

# achou um errinho que pertence a um commit antigo (1a2b3c4)?
$ git add form.html
$ git commit --fixup 1a2b3c4
$ git rebase -i --autosquash main   # o Git já posiciona o fixup no lugar certo
MergeRebase
HistóricoPreserva tudo como aconteceuLinear e limpo
Commits existentesNão alteraRecria (hashes novos)
Seguro em branch compartilhada?SimNão
Melhor usoIntegrar trabalho na mainAtualizar e arrumar sua branch local

Crie uma branch e faça 4 commits pequenos com mensagens ruins. Use git rebase -i HEAD~4 para transformá-los em 2 commits com mensagens boas. Confira com git log --oneline.

Aula 15

Stash: a gaveta de trabalho em andamento

Guardar alterações pela metade sem precisar comitar.

Situação real: você está no meio de uma funcionalidade e o chefe chega: "urgente, tem um bug em produção!". Seu código está pela metade, não dá para comitar. O que fazer? Guarda na gaveta!

$ git stash                              # guarda as alterações e limpa a área de trabalho
$ git stash push -m "formulário pela metade"   # com uma descrição
$ git stash -u                           # inclui arquivos novos (não rastreados)

# ... vai para outra branch, corrige o bug, volta ...

$ git stash list
stash@{0}: On feature/contato: formulário pela metade
stash@{1}: WIP on main: 3f9a1c2 Cria estrutura inicial

$ git stash show -p stash@{0}            # vê o conteúdo
$ git stash pop                          # devolve o último e remove da lista
$ git stash apply stash@{1}              # devolve um específico e MANTÉM na lista
$ git stash drop stash@{1}               # apaga um
$ git stash clear                        # apaga todos
$ git stash branch nova-branch           # cria uma branch a partir do stash
$ git stash push -m "só o css" style.css # guarda apenas um arquivo
Analogia

O stash é uma pilha de pratos: o último que entra é o primeiro que sai (stash@{0}). O pop tira o prato de cima; o apply só olha e copia, deixando o prato lá.

Não use o stash como depósito

Stash esquecido vira lixo que você não lembra o que era. Se o trabalho vai demorar, prefira um commit numa branch própria.

Desafio 15

Edite dois arquivos, guarde com git stash push -m "teste", troque para outra branch, faça um commit qualquer, volte e recupere com git stash pop.

Aula 16

Tags, versões e releases

Marcar versões oficiais do seu projeto.

Uma tag é uma etiqueta fixa num commit. Diferente da branch, ela não anda. Serve para marcar marcos importantes, como "versão 1.0 que foi para produção".

Versionamento Semântico (SemVer)

O padrão do mercado é MAJOR.MINOR.PATCH, por exemplo v2.4.1:

ParteAumenta quando...Exemplo
MAJORMudança que quebra compatibilidade1.9.3 → 2.0.0
MINORFuncionalidade nova, compatível2.0.0 → 2.1.0
PATCHCorreção de bug2.1.0 → 2.1.1
 
# tag anotada (recomendada: guarda autor, data e mensagem)
$ git tag -a v1.0.0 -m "Primeira versão pública"

# tag leve (só um nome apontando para o commit)
$ git tag v1.0.0-rc1

# marcar um commit antigo
$ git tag -a v0.9.0 8b21e07 -m "Versão beta"

$ git tag                       # lista
$ git tag -l "v1.*"             # filtra
$ git show v1.0.0               # detalhes
$ git describe --tags           # "v1.0.0-3-gc4d0f55" = 3 commits depois da v1.0.0

# tags NÃO sobem com git push normal!
$ git push origin v1.0.0        # envia uma
$ git push --tags               # envia todas
$ git push --follow-tags        # envia commits + tags anotadas ligadas a eles

# apagar
$ git tag -d v1.0.0-rc1
$ git push origin --delete v1.0.0-rc1

# ver o código de uma versão antiga
$ git switch --detach v1.0.0

Releases no GitHub

Uma Release é uma tag com página bonita no GitHub: notas da versão, arquivos para download e changelog. Crie em Releases → Draft a new release, ou pelo terminal:

$ gh release create v1.0.0 --generate-notes
$ gh release create v1.1.0 ./dist/app.zip --title "Versão 1.1" --notes "Novo modo escuro"
Desafio 16

Crie a tag anotada v1.0.0 no seu site, envie para o GitHub e transforme-a numa Release com notas geradas automaticamente.

Aula 17

Arsenal avançado

As ferramentas que separam quem usa Git de quem domina Git.

git reflog: o salva-vidas

Fez um reset --hard errado? Apagou uma branch sem querer? Calma. O reflog registra todo lugar por onde o HEAD passou. Por padrão, as entradas ficam guardadas por 90 dias, e as de commits que ficaram sem nenhuma branch apontando para eles, por 30 dias. Então, se agir rápido, praticamente nada comitado se perde de verdade.

$ git reflog
e19a7b3 HEAD@{0}: reset: moving to HEAD~2
a7c3d91 HEAD@{1}: commit: Adiciona galeria de fotos
c4d0f55 HEAD@{2}: commit: Ajusta menu

# volta para antes do desastre
$ git reset --hard HEAD@{1}

# ou recupera o commit numa branch nova
$ git branch galeria-recuperada a7c3d91

git cherry-pick: pegando um commit específico

Precisa de só um commit de outra branch (por exemplo, uma correção), sem trazer o resto? Escolha a cereja do bolo:

$ git switch main
$ git cherry-pick 9f8e7d6
$ git cherry-pick -x 9f8e7d6        # anota na mensagem de onde veio
$ git cherry-pick a1b2c3d..f4e5d6c  # um intervalo
$ git cherry-pick --continue        # após resolver conflito
$ git cherry-pick --abort

git bisect: caçando o commit que criou o bug

O sistema funcionava na v1.0 e agora, 200 commits depois, está quebrado. Testar um por um? Nada disso! O bisect faz uma busca binária: em vez de 200 testes, uns 8.

$ git bisect start
$ git bisect bad                 # a versão atual está com bug
$ git bisect good v1.0.0         # nessa versão funcionava
Bisecting: 100 revisions left to test after this (roughly 7 steps)

# o Git te leva para um commit no meio. Teste e responda:
$ git bisect good                # ou: git bisect bad
# ... repita até ele dizer: "abc1234 is the first bad commit"

$ git bisect reset               # volta para onde você estava

# modo automático: o Git roda seus testes sozinho
$ git bisect run npm test

git worktree: duas branches abertas ao mesmo tempo

Em vez de fazer stash para trocar de branch, abra outra branch numa pasta separada, compartilhando o mesmo repositório:

$ git worktree add ../meu-site-hotfix hotfix/pagamento
$ git worktree add -b feature/blog ../meu-site-blog   # cria a branch junto
$ git worktree list
$ git worktree remove ../meu-site-hotfix

Submódulos: um repositório dentro do outro

$ git submodule add https://github.com/org/biblioteca.git libs/biblioteca
$ git clone --recurse-submodules URL          # clona já com os submódulos
$ git submodule update --init --recursive     # se esqueceu do --recurse-submodules
$ git submodule update --remote               # atualiza para a versão mais nova

git grep: busca turbinada

$ git grep "TODO"                 # busca nos arquivos rastreados
$ git grep -n "apiKey"            # com número da linha
$ git grep -c "console.log"       # conta por arquivo
$ git grep "login" v1.0.0         # busca numa versão antiga

Aliases: crie seus próprios atalhos

$ git config --global alias.st "status -sb"
$ git config --global alias.lg "log --oneline --graph --all --decorate"
$ git config --global alias.last "log -1 HEAD --stat"
$ git config --global alias.desfaz "reset --soft HEAD~1"

$ git lg        # agora funciona!

Hooks: automações locais

Hooks são scripts que o Git executa em momentos específicos. Ficam em .git/hooks/. Exemplo: impedir commits com console.log esquecido.

#!/bin/sh
if git diff --cached | grep -q "console.log"; then
  echo "Ops! Você esqueceu um console.log. Commit cancelado."
  exit 1
fi

No Windows, o Git Bash executa o hook normalmente. Basta salvar o arquivo sem extensão (nada de pre-commit.txt) com finais de linha LF.

Dê permissão de execução:

$ chmod +x .git/hooks/pre-commit

Dê permissão de execução:

$ chmod +x .git/hooks/pre-commit

Hooks em .git/hooks não vão para o GitHub. Para compartilhar com a equipe, use ferramentas como Husky (JavaScript) ou pre-commit (Python), ou aponte o Git para uma pasta versionada com git config core.hooksPath .githooks.

Commits assinados (selo "Verified")

Qualquer um pode configurar user.name com o seu nome. Assinar commits prova que foi você. Dá para usar a mesma chave SSH da Aula 11:

$ git config --global gpg.format ssh
$ git config --global user.signingkey ~/.ssh/id_ed25519.pub
$ git config --global commit.gpgsign true
$ git config --global tag.gpgsign true

Depois cadastre a mesma chave pública no GitHub em SSH and GPG keys → New SSH key, escolhendo o tipo Signing Key. Seus commits ganham o selo verde Verified.

Git LFS: arquivos grandes

O Git não foi feito para vídeos, PSDs e datasets gigantes. O Git LFS guarda esses arquivos à parte e deixa só um "ponteiro" no repositório.

$ git lfs install
$ git lfs track "*.psd"
$ git lfs track "videos/*.mp4"
$ git add .gitattributes
$ git commit -m "Configura Git LFS"

HEAD destacado (detached HEAD)

Quando você faz git switch --detach abc1234 ou git checkout v1.0.0, o HEAD aponta direto para um commit, e não para uma branch. Você pode olhar e testar à vontade, mas commits feitos aí ficam "soltos". Se quiser manter algo, crie uma branch:

$ git switch -c experimento-a-partir-da-v1
# ou, para só sair dali:
$ git switch main

Outros comandos úteis

$ git add -p                         # escolhe PEDAÇOS de um arquivo para o commit
$ git commit --allow-empty -m "Dispara o deploy"   # commit sem mudanças
$ git archive --format=zip -o site.zip HEAD        # exporta o projeto sem a pasta .git
$ git restore -p arquivo             # descarta pedaços específicos
$ git range-diff main feature-v1 feature-v2        # compara duas versões de uma branch
$ git gc                             # compacta e otimiza o repositório
$ git fsck                           # verifica a integridade
$ git count-objects -vH              # tamanho do repositório
$ git help rebase                    # manual completo de qualquer comando
$ git rebase -h                      # resumo rápido das opções
Desafio 17

Faça 3 commits, rode git reset --hard HEAD~3 (sim, de propósito!) e recupere tudo usando o git reflog. Depois crie o alias git lg e use-o para ver o resultado.

Aula 18

Boas práticas e fluxos de trabalho profissionais

Como as equipes de verdade organizam o trabalho com Git.

Mensagens de commit que contam a história

Compare. Qual histórico você prefere herdar?

Ruim
a1b2c3d ajustes
d4e5f6a arrumei
b7c8d9e asdasd
f0a1b2c agora vai
Bom
a1b2c3d feat: adiciona login com Google

b7c8d9e docs: explica variáveis do .env
f0a1b2c refactor: extrai validação de CPF

Conventional Commits

Um padrão muito adotado: tipo(escopo opcional): descrição curta no imperativo.

TipoUso
featNova funcionalidade
fixCorreção de bug
docsSó documentação
styleFormatação, sem mudar lógica
refactorReorganização de código sem mudar comportamento
testTestes
perfMelhoria de desempenho
build / ciDependências, build, pipelines
choreTarefas de manutenção
  • Título com até uns 50 caracteres, sem ponto final.
  • Use o imperativo: "adiciona", "corrige" (complete a frase "este commit...").
  • Se precisar explicar, pule uma linha e escreva o corpo dizendo por quê.
  • Mudança que quebra compatibilidade: feat!: ... ou BREAKING CHANGE: no corpo.

Fluxos de trabalho

GitHub Flow

Uma main sempre pronta para produção + branches curtas por funcionalidade + PR. Simples e ideal para a maioria dos projetos e para deploy contínuo.

Git Flow

Branches fixas main e develop, mais feature/*, release/* e hotfix/*. Mais cerimônia; útil para software com versões planejadas.

Trunk-Based

Todos integram na main várias vezes por dia, com branches de horas. Exige testes automatizados fortes e feature flags.

Checklist do profissional

  • Commits pequenos e atômicos: uma ideia por commit.
  • Nunca trabalhe direto na main; crie uma branch.
  • git pull antes de começar e antes de abrir PR.
  • Revise o que vai comitar com git diff --staged.
  • Nunca comite segredos (senhas, tokens, .env). Use .gitignore e um .env.example sem valores reais.
  • Proteja a main no GitHub: Settings → Rules (ou Branches), exigindo PR e aprovação.
  • Apague branches depois do merge.
  • Escreva um bom README.
  • Automatize testes com GitHub Actions (arquivos YAML em .github/workflows/).
Desafio 18

Reescreva (com git rebase -i numa branch sua) as mensagens dos seus últimos commits seguindo o Conventional Commits. Depois ative uma regra de proteção na main do seu repositório exigindo Pull Request.

Aula 19

Projeto final: o ciclo completo

Juntar tudo num projeto real, do git init à release.

Chegou a hora de mostrar que você aprendeu. Siga o roteiro abaixo sem olhar as aulas anteriores (se travar, tudo bem consultar!). Vamos criar o projeto lista-de-tarefas.

# 1. criar e configurar
$ mkdir lista-de-tarefas && cd lista-de-tarefas
$ git init
$ echo "# Lista de Tarefas" > README.md
$ printf "node_modules/\n.env\n*.log\n" > .gitignore
$ git add .
$ git commit -m "chore: estrutura inicial do projeto"

# 2. publicar no GitHub
$ gh repo create lista-de-tarefas --public --source=. --remote=origin --push
#   (ou crie pelo site e use: git remote add origin URL && git push -u origin main)

# 3. primeira funcionalidade numa branch
$ git switch -c feature/adicionar-tarefa
$ echo "<input id='nova'><button>Adicionar</button>" > index.html
$ git add index.html
$ git commit -m "feat: campo para adicionar tarefa"
$ git push -u origin feature/adicionar-tarefa
$ gh pr create --fill
$ gh pr merge --squash --delete-branch
#   (o gh já apaga a branch no GitHub e na sua máquina e te leva para a main)

# 4. garantir que a main local está atualizada
$ git switch main
$ git pull
$ git branch                      # a feature não aparece mais

# 5. corrigir um bug com revert
$ echo "<p>bug</p>" >> index.html
$ git commit -am "feat: texto experimental"
$ git push
$ git revert --no-edit HEAD
$ git push

# 6. lançar a versão
$ git tag -a v1.0.0 -m "Primeira versão"
$ git push origin v1.0.0
$ gh release create v1.0.0 --generate-notes

# 7. admirar o resultado
$ git log --oneline --graph --all --decorate
Parabéns, você chegou até aqui!

Se você praticou cada aula, agora sabe versionar, comitar, criar branches, resolver conflitos, colaborar no GitHub, desfazer erros e lançar versões. Isso é o que o mercado espera de qualquer desenvolvedor. O próximo passo é usar Git em todos os seus projetos, até os pequenos. A prática é o que transforma comando decorado em reflexo.

Desafio 19 (o grande desafio)

Chame um amigo. Um cria o repositório, o outro faz um fork. Cada um abre um PR para o outro, provoquem um conflito no mesmo arquivo, resolvam, revisem o código um do outro e publiquem uma release v1.0.0 juntos.

Apêndice A

Socorro! Erros comuns e como sair deles

As situações que todo mundo enfrenta. Guarde esta página nos favoritos.

Fiz commit na branch errada (ainda não enviei)
$ git branch branch-certa       # cria a branch certa apontando para o commit atual
$ git reset --hard HEAD~1       # volta a branch errada um commit
$ git switch branch-certa       # seu commit está aqui

Se a branch certa já existe: anote o hash, desfaça com git reset --hard HEAD~1, vá para a branch certa e use git cherry-pick hash.

Comitei uma senha, token ou arquivo .env
Primeiro de tudo: troque a senha ou revogue o token

Se o commit foi para o GitHub, considere o segredo vazado, mesmo que você apague depois. Robôs varrem o GitHub atrás disso em minutos.

Se ainda não enviou: git rm --cached .env, adicione ao .gitignore e use git commit --amend (ou git reset --soft). Se já enviou, além de revogar a credencial, é preciso reescrever o histórico com a ferramenta git filter-repo (ou o BFG Repo-Cleaner) e forçar o envio, combinando antes com a equipe.

error: failed to push some refs / [rejected] non-fast-forward

Tem commits no remoto que você não tem. Traga primeiro:

$ git pull --rebase
$ git push
Authentication failed / Support for password authentication was removed

Você tentou usar a senha do site. Use o login pelo navegador (gh auth login ou Git Credential Manager), uma chave SSH ou um Personal Access Token. Veja a Aula 11.

Permission denied (publickey)
$ ssh-add -l                    # a chave está carregada no agente?
$ ssh-add ~/.ssh/id_ed25519     # se não estiver, adicione
$ ssh -T git@github.com         # testa de novo
$ git remote -v                 # a URL está no formato git@github.com:...?

Confira também se a chave pública está cadastrada em Settings → SSH and GPG keys.

fatal: not a git repository

Você está numa pasta que não é um repositório. Use pwd para ver onde está e cd até a pasta do projeto, ou rode git init se for um projeto novo.

fatal: refusing to merge unrelated histories

Acontece quando você criou o repositório no GitHub com README e já tinha um projeto local com histórico próprio. Junte os dois uma vez:

$ git pull origin main --allow-unrelated-histories
You are in 'detached HEAD' state

Você está olhando um commit específico, fora de qualquer branch. Para guardar o que fez ali: git switch -c nome-da-branch. Para só voltar: git switch main.

warning: LF will be replaced by CRLF

É só um aviso sobre finais de linha (Aula 03). Para a equipe toda ter o mesmo comportamento, crie um arquivo .gitattributes na raiz:

* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary
Coloquei no .gitignore e o arquivo continua aparecendo

Ele já era rastreado. Rode git rm --cached arquivo (ou -r para pastas) e comite.

Apaguei uma branch / fiz reset --hard e perdi commits

git reflog, encontre o hash e recrie: git branch recuperada hash. Veja a Aula 17.

Quero desistir de um merge ou rebase no meio

git merge --abort, git rebase --abort ou git cherry-pick --abort. Tudo volta a como estava antes de você começar.
